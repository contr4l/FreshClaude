# 委托式开发示例：浏览器自动化

## 场景
用户需要自动化登录公司内部系统并执行操作

## 日期
2026-04-08

## 模块
1.1 核心概念 - 委托vs指令实践

---

## 对话过程

### Prompt 1（初始委托）
```
创建一个脚本，它可以在我的电脑上登陆http://dev.alfred.nvidia.com
```

### Claude 响应
- 识别为"委托式"请求
- 指出信息不足：登录方式、技术选型、登录后目标
- 没有立即动手，而是澄清需求

### Prompt 2（补充信息）
```
SSO登陆，浏览器自动化，登陆后我可能要访问相关页面完成订车或者是更新某些bench的固件的操作
```

### Claude 响应
完整输出：
- `alfred_automation.py` - 主脚本（150+行）
- `README.md` - 使用说明
- `requirements.txt` - 依赖声明

---

## 分析

### 这是好的委托吗？

**第一个prompt**：
- ✅ 表达了目标（登录网站）
- ❌ 缺少关键信息（如何登录、用什么技术）
- 结果：Claude 主动澄清而非盲目执行

**第二个prompt**：
- ✅ 补充了技术约束（SSO、浏览器自动化）
- ✅ 说明了后续用途（订车、更新固件）
- ✅ 给了足够的上下文让 Claude 做决策

### Claude 的决策过程

1. **技术选型**：选择 Playwright 而非 Selenium（更现代）
2. **架构设计**：类结构而非函数堆叠（便于扩展）
3. **务实考虑**：
   - SSO 需要手动介入（无法完全自动化）
   - 保存登录状态（避免重复登录）
   - 业务逻辑留框架（需要实际页面信息才能完善）

### 委托式开发的特点

| 对比 | 指令式 | 委托式（本例） |
|------|--------|---------------|
| 用户输入 | "用Selenium写个登录脚本" | "我要自动化登录和操作" |
| Claude 角色 | 执行者 | 决策者+执行者 |
| 输出范围 | 一个函数 | 完整项目结构 |
| 技术选型 | 用户决定 | Claude 建议 |
| 边界情况 | 用户提醒才处理 | 主动考虑（如SSO特殊性） |
